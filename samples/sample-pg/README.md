# sample-pg: CodeAtlas 검증용 PostgreSQL 샘플 프로젝트

PostgreSQL 만 쓰는 작은 "주문 관리" 시스템이다. F-019(PostgreSQL 지원)의 통합 검증 기준으로 쓴다(F-019-R36, F-019-AC34). `samples/sample-shop`(Oracle·DB2)보다 훨씬 작고, pg_dump 평문 DDL · PL/pgSQL 루틴 · MyBatis 매퍼의 PostgreSQL 구문과 까다로운 경우를 손으로 만들어 담았다.

- 분석 대상은 이 폴더(`samples/sample-pg`) 전체다. 정답 목록의 모든 경로와 노드 ID 는 **이 폴더를 프로젝트 루트로** 한 상대 경로다.
- 옵션 없이 분석한다(`--dialect` 를 주지 않는다). 방언은 `application.yml` 의 JDBC URL 과 SQL 파일의 내용 특징으로 알아내야 한다. SQL 파일 경로에는 방언 이름이 없다(`db/01_schema.sql`).
- 실행하거나 빌드하는 프로젝트가 아니다. `pom.xml` 이 없다. 모든 파일은 문법적으로 올바르게 썼다(깨진 입력은 없다).
- 정답(`expected/`)은 분석기 없이 SQL 과 코드를 읽고 사람이 판단해서 쓴 것이다. 분석기 결과로 정답을 고치지 않는다. 정답이 틀렸다고 판단되면 소스의 근거 줄을 확인하고 고친다.
- **실제 PostgreSQL 에서 실행해 보지 않았다(DB 없음).** SQL 은 PostgreSQL 13 이상의 문법으로 눈으로 검토했을 뿐이다(7절).
- 이름은 대문자로 정규화되고 스키마는 빠진다: `public.orders` → `db:table:ORDERS`.

## 2. `db/01_schema.sql` 이 pg_dump 출력과 다른 점

파일은 pg_dump 평문 출력의 순서와 꼴을 따른다: 머리말 `SET …`, `SELECT pg_catalog.set_config(...)`, `CREATE EXTENSION`, `CREATE TYPE … AS ENUM`, 객체마다 붙는 `-- Name: …; Type: …` 주석, `CREATE TABLE public.…`, `CREATE SEQUENCE` + `ALTER SEQUENCE … OWNED BY`, `ALTER TABLE ONLY … ALTER COLUMN … SET DEFAULT nextval('…'::regclass)`, `COPY … FROM stdin` 데이터와 `\.`, `SELECT pg_catalog.setval(...)`, `ALTER TABLE ONLY … ADD CONSTRAINT … PRIMARY KEY / UNIQUE / FOREIGN KEY`, `CREATE INDEX … USING btree/gin`, `COMMENT ON`, `ALTER … OWNER TO`, `GRANT`/`REVOKE`.

검증 범위를 넓히려고 실제 pg_dump 라면 내지 않을 꼴을 일부러 섞었다.

| 섞은 것 | 위치 | pg_dump 라면 |
|---|---|---|
| `serial`, `bigserial` 타입 | `products.id`(111행), `order_items.id`(179행) | `integer`/`bigint` + `CREATE SEQUENCE` + `SET DEFAULT nextval(...)` 으로 풀어서 낸다 |
| 컬럼 정의 안의 `GENERATED BY DEFAULT AS IDENTITY` | `payments.id`(195행) | `ALTER TABLE … ALTER COLUMN … ADD GENERATED … AS IDENTITY (…)` 로 따로 낸다 |
| `LIKE public.orders INCLUDING …` | `orders_archive`(222행) | 컬럼을 풀어서 낸다 |
| `CREATE TABLE … PARTITION OF … FOR VALUES …` | `order_events_2026`(262행) | 컬럼을 적은 `CREATE TABLE` 뒤에 `ALTER TABLE ONLY … ATTACH PARTITION` 으로 낸다 |
| 시퀀스 소유자를 `ALTER TABLE …`(97행)과 `ALTER SEQUENCE …`(165행) 두 꼴로 | `customers_id_seq`, `orders_id_seq` | 15 이하는 `ALTER TABLE`, 16 이상은 `ALTER SEQUENCE` 한 가지로만 낸다 |
| 주석으로 적은 `ALTER TABLE … FOREIGN KEY` | 478~481행 | 없다 |
| `\connect shop` 만 있고 `CREATE DATABASE` 가 없다 | 8행 | `-C` 옵션이면 둘 다 낸다 |

외래 키 가운데 `order_items.product_id → products.id`, `payments.order_id → orders.id`, `order_events.order_id → orders.id` 는 **일부러 DDL 에 두지 않았다.** 조인으로만 드러난다(관계 추론 대상, `expected/erd-expected.md`).

## 3. 일부러 넣은 미지원 구문

F-019 의 범위 밖이지만 pg_dump 출력에 실제로 나오는 구문이다. 분석이 멈추지 않는지 본다. F-019-AC34 의 "`PARSE_FAILED`·`UNSUPPORTED_SYNTAX` 가 샘플의 일부러 넣은 미지원 구문 목록에 있는 것뿐"에서 말하는 목록이 이것이다(같은 표가 `expected/expected-unresolved.md` 4절에 있다).

| # | 위치 | 구문 | 기대 |
|---|---|---|---|
| N1 | `db/01_schema.sql:517` | `REFRESH MATERIALIZED VIEW public.mv_daily_sales;` | 이 줄에 한해 진단이 남아도 되고 조용히 넘겨도 된다. 이 줄에서 테이블·구문 노드가 나오면 안 된다 |

깨진 입력(`broken/`)은 없다. `db/02_routines.sql:208` 의 `LANGUAGE c` 함수 `fast_hash` 는 미지원 구문이 아니다: 루틴 노드 `db:routine:FAST_HASH` 만 있고 **`language` 속성이 없어야 하며 진단도 없어야 한다**(F-019-R24, F-019-AC22). "속성이 없다"는 것은 정답 JSON 의 형식으로 적을 수 없어 여기에 적는다.

## 5. 함정 (있으면 안 되는 관계)

`expected/must-not-have-edges.json` 의 각 항목 `note` 는 `함정 <번호>.` 로 시작한다.

| # | 함정 | 나오는 곳 |
|---|---|---|
| 1 | `ONLY` 라는 테이블 | `ALTER TABLE ONLY public.x …` 12곳(주석 속 1곳 제외), `UPDATE ONLY orders o` |
| 2 | CTE 이름이 테이블이 됨: `PAID`, `TOUCHED`, `TREE`, `MOVED` | `markPaidOrders`, `selectReferralTree`, 프로시저 `ARCHIVE_ORDERS` |

### 이 샘플에서 정한 표기

- **루틴 본문 구문의 ID** 는 sample-shop 과 같이 `sql:stmt:<루틴 이름>:<줄>` 로 적고 `fromRoutine` 을 함께 적었다. 줄은 `db/02_routines.sql` 의 줄(달러 인용 안이어도 원본 파일 기준, F-019-R25)이고 **SQL 키워드(SELECT/INSERT/UPDATE/DELETE/WITH)가 시작하는 줄**이다. `FOR r IN 쿼리` 와 `RETURN QUERY 쿼리` 는 그 안의 `SELECT` 줄, 동적 SQL 은 `EXECUTE` 문장의 첫 줄이다. 줄 해석이 달라도 `fromRoutine` 으로 느슨하게 통과한다. 줄까지 정확히 보는 항목은 `CONTAINS`(`db:routine:CLOSE_ORDER` → `sql:stmt:CLOSE_ORDER:77`) 하나다.
- **`LANGUAGE sql` 루틴의 본문 구문**도 같은 형식이다(`sql:stmt:CALC_ORDER_TOTAL:16`).
- **DO 블록**은 계약의 익명 블록 규칙대로 블록의 구문 노드 하나(`sql:stmt:db/02_routines.sql:216`)에서 `READS`·`WRITES`·`CALLS` 가 나가는 것으로 적고 `fromFile`·`line` 을 함께 적었다.
- **뷰 정의 쿼리**는 `sql:stmt:db/01_schema.sql:<CREATE 줄>` 이다(272, 290).
- **`COPY … FROM stdin` 적재**는 `sql:stmt:db/01_schema.sql:<COPY 줄>` 에서 테이블로 가는 `WRITES`(`op=INSERT`)로 적었다(`fromFile`·`line` 으로 느슨하게 통과). 적재 묶음 노드(`dataLoad=true`, `rowCount`)는 ID 의 줄이 계약에 "첫 INSERT 줄"로만 적혀 있어 `certainty: low` 다.
- **트리거**: `CREATE TRIGGER` 의 이름이 트리거 루틴(`db:routine:ORDERS_AUDIT`, `routineType=TRIGGER`)이고, 거기서 `TRIGGERS_ON` 과 트리거 함수로의 `CALLS` 가 나간다(F-019-AC27). 트리거 함수(`db:routine:TRG_ORDERS_AUDIT`)는 `routineType=FUNCTION` 이다.
- **dataType** 은 원문을 대문자로 적었다(`CHARACTER VARYING(120)`, `TIMESTAMP WITH TIME ZONE`, `TEXT[]`, `SERIAL`). 대조기는 공백을 지우고 비교한다.
- **추론 FK** 는 sample-shop 과 같은 기준("FK 제약이 없고, 자식 컬럼이 부모의 단일 컬럼 PK 전체와 등치 조인")으로 3개를 넣었다.
- 뷰를 읽는 구문은 sample-shop 과 같이 `to` 를 `db:view:`, `altTo` 에 `db:table:` 을 넣고 `certainty: low` 로 두었다.

### 정답에 넣지 않은 것

사실 자체는 있지만 계약이나 spec 이 표현을 정하지 않아 단정하지 않은 것이다. 나와도 되고 안 나와도 된다(함정에도 넣지 않았다).

| 넣지 않은 것 | 이유 |
|---|---|
| `SET DEFAULT nextval('public.…_seq'::regclass)`(308, 315행)와 `SELECT pg_catalog.setval(...)`(353, 360행)의 시퀀스 참조 | F-019-R16·R22 는 "참조로 기록한다"면서 pg_dump 부속 구문은 "구문 노드를 만들지 않는다"고 한다. 어느 노드에서 나가는 엣지인지 정해지지 않았다 |
| `serial`·`bigserial`·IDENTITY 가 암묵적으로 만드는 시퀀스(`PRODUCTS_ID_SEQ` 등) | `CREATE SEQUENCE` 문이 없다. 노드를 만들지 정해지지 않았다 |
| 테이블의 `indexes`, `uniqueKeys`, 컬럼의 `indexed`·`unique` | 부분 인덱스·식 인덱스·연산자 클래스가 낀 항목의 표기가 정해지지 않았다(F-019-AC20 은 식 인덱스를 "기록하거나 생략"이라고 한다). 틀린 컬럼이 생기지 않는지만 함정 10 으로 본다 |
| `ORDERS.STATUS`, `ORDERS_ARCHIVE.STATUS` 의 `dataType` | 타입이 `public.order_status` 다. 스키마를 뗄지 정해지지 않았다 |
| `LIKE`·`INHERITS`·`PARTITION OF` 로 온 컬럼의 `nullable`, `defaultValue` | F-019-R20 은 "컬럼을 넣는다"까지만 정한다. 순번과 타입만 적었다 |
| 컬럼의 `defaultValue`, 테이블·루틴의 `schema`(`ORDERS` 에만 `certainty: low` 로) | 캐스트가 든 기본값 원문과 소문자 스키마의 정규화 표기가 정해지지 않았다 |
| 외래 키의 `constraint` 이름 | 소문자 제약 이름의 정규화가 정해지지 않았다 |
| `upsertCustomer`·`putSession` 의 `WRITES.op` | `ON CONFLICT … DO UPDATE` 를 `INSERT` 로 적을지 `MERGE` 로 적을지 정해지지 않았다 |
| `markPaidOrders` 의 `statementType` | 본체는 SELECT, CTE 는 UPDATE 둘이다 |
| 루틴의 `statementCount`, `returnType`, `typeRefs`, `triggerEvent`, `CLOSE_ORDER` 밖의 `parameters` | `PERFORM f(..)` 가 구문 노드를 만드는지에 따라 수가 달라지고, 나머지는 표기 예가 spec 에 없다. `parameters` 는 F-019-AC22 에 표기가 있는 `CLOSE_ORDER` 만 적었다 |
| `PERFORM f(..)` 호출의 `callType` | `procedure`(문장 자리)인지 `function`(식 안)인지 정해지지 않았다. 엣지만 적었다 |
| CTE·LATERAL 을 거친 조인의 `JOINS` (`c.id = paid.customer_id`, `ch.referrer_id = t.id`) | CTE 컬럼을 원본 테이블로 푸는지는 구현에 달렸다. LATERAL 의 상관 조건은 `certainty: low` 로 넣었다 |
| `RETURNING` 과 `INSERT … ON CONFLICT … SET x = customers.profile \|\| …` 이 대상 테이블의 테이블 수준 `READS` 를 만드는지 | 계약은 UPDATE·DELETE·MERGE 대상의 규칙만 적었다 |
| 컬럼 수준 `READS`·`WRITES` 대부분 | 별칭으로 한정했거나 INSERT 컬럼 목록·SET 대상이라 소속이 분명한 10개만 넣었다 |
| 뷰의 컬럼 노드, 뷰 정의 쿼리의 `JOINS` | 뷰 컬럼의 이름·타입 표기와 근거 구문 ID 를 단정하지 않았다 |
| `selectTimeline` 의 `FROM order_timeline(..)` → `CALLS` | `certainty: low` 로 넣었다. FROM 의 함수를 호출로 기록하는지 spec 에 없다 |
| 풀리지 않는 동적 SQL 의 미해결 엣지(`archive_orders` 173행) | JSON 형식으로는 미해결 엣지를 적지 않는다(sample-shop 과 같다). `expected-unresolved.md` U1 에 적었다 |
| `FILE` 노드와 `FILE → …` `CONTAINS`, `DB_TABLE → DB_COLUMN` `CONTAINS`, 컨트롤러의 빈(`spring:bean:orderController`), `ASSOCIATES`·`DEPENDS_ON` | sample-shop 정답도 넣지 않은 것이다 |
| `FAST_HASH` 에 `language` 가 없다는 것, N1 밖의 위치에 `PARSE_FAILED`·`UNSUPPORTED_SYNTAX` 가 없다는 것 | "없다"는 이 JSON 형식으로 적을 수 없다. 통합 테스트가 진단을 따로 봐야 한다 |

## 8. 샘플을 고칠 때

- `db/01_schema.sql`, `db/02_routines.sql` 의 정답은 **줄 번호에 묶여 있다**: 루틴 안 구문(`sql:stmt:CLOSE_ORDER:77`), 뷰 정의·`COPY`·DO 블록의 `fromFile`/`line`, `expected-unresolved.md`, 이 README 4·5절의 위치. 줄을 넣거나 빼면 정답도 고쳐야 한다. `check_expected.py` 가 어긋난 구문 줄을 잡아 준다(README 와 `note` 의 줄은 잡지 못한다).
- `COPY` 데이터 줄의 구분자는 탭이다. 편집기가 탭을 공백으로 바꾸면 데이터 줄 수(`rowCount`)는 그대로지만 pg_dump 의 꼴이 깨진다.
- 매퍼 XML 과 Java 는 줄 번호에 묶인 정답이 거의 없다(`expected-unresolved.md` 의 D2·D3 과 함정 14 의 `note`).
- 새 패턴을 넣으면 4절의 표와 정답 목록에 함께 적는다. F-019 의 범위(spec 2절) 밖의 구문은 3절의 목록에 올린다.
