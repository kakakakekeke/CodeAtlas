# 문서 지도

이 폴더가 프로젝트 문서의 유일한 원본이다. Obsidian으로 이 폴더(또는 저장소 루트)를 열어 쓴다.

| 문서 | 경로 | 작성 단위 | 언제 고치는가 |
|---|---|---|---|
| PRD | `prd.md` | 프로젝트당 1개 | 목표나 범위가 바뀔 때 |
| 기능정의서 | `features.md` | 프로젝트당 1개 | 기능을 추가·폐기하거나 상태가 바뀔 때 |
| 기능 명세 | `specs/F-xxx-이름/spec.md` | 기능당 1개 | 요구사항이 바뀔 때 |
| 기능 설계 | `specs/F-xxx-이름/design.md` | 큰 기능만 | 구현 방식이 바뀔 때 |
| 작업 목록 | `specs/F-xxx-이름/tasks.md` | 기능당 1개 | 작업을 진행할 때마다 |
| 아키텍처 | `architecture.md` | 프로젝트당 1개 | 구조가 바뀔 때 |
| 결정 기록(ADR) | `decisions/NNNN-제목.md` | 결정당 1개 | 새 결정이 생길 때 (기존 것은 수정하지 않음) |
| 변경 기록 | `../CHANGELOG.md` (저장소 루트) | 프로젝트당 1개 | 사용자가 알아챌 수 있는 변경을 할 때마다 |

## 어떤 문서를 쓸지 고르기

| 변경 크기 | 쓰는 문서 |
|---|---|
| 버그 수정, 작은 변경 | 변경 기록 항목만. 에이전트의 plan 모드로 처리 |
| 보통 기능 | features.md 행 + spec.md + tasks.md + 변경 기록 항목 |
| 큰 기능 | 위에 더해 design.md, 필요하면 ADR |

## ID 규칙

- 기능: `F-001` (features.md에서 부여)
- 요구사항: `F-001-R1` (spec.md에서 부여)
- 수용 기준: `F-001-AC1`
- ADR: `0001`부터 순번
- ID는 재사용하지 않는다.

## 새 기능 시작하기

1. `features.md`에 행을 추가하고 기능 ID를 부여한다.
2. `specs/F-xxx-이름/` 폴더를 만들고 `_templates/`의 spec.md, tasks.md를 복사한다. 큰 기능이면 design.md도 복사한다.
3. 에이전트에게 spec 초안을 쓰게 하고, 요구사항이 의도와 맞는지 직접 검토한다.
4. `[확인 필요]`가 모두 해소되면 spec의 status를 `approved`로 바꾸고 구현을 시작한다.

이 프로젝트에서 쓰는 방식
- spec의 `status` 값은 `draft | approved | implemented`를 쓴다. 구현이 끝나고 수용 기준이 모두 통과하면 `implemented`로 바꾼다.
- 개발은 TDD로 하고, 수용 기준 ID(`F-xxx-ACn`)를 테스트 이름이나 `@DisplayName`에 적는다([AGENTS.md](../AGENTS.md)의 "개발 방식: TDD").

## 검토할 때 볼 것

- 요구사항이 실제 의도와 맞는가. 형식이 맞아도 내용이 틀릴 수 있다.
- 에이전트가 요청하지 않은 요구사항을 넣지 않았는가.
- 다이어그램의 화살표(의존 관계)가 코드와 맞는가.
