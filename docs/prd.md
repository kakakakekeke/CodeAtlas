# PRD: CodeAtlas

<!-- 한두 쪽 분량으로 유지한다. 구현 방법은 적지 않는다. -->

## 1. 문제
Spring과 MyBatis로 만든 웹·배치 Java 시스템은 하나의 처리 흐름이 화면(JSP, JS) → Controller → Service → Mapper → SQL → 테이블·프로시저로 여러 언어와 파일에 걸쳐 있다. IDE의 호출 추적은 Java 안에서만 이어지고 매퍼 XML, SQL, 프로시저, 화면 스크립트 경계에서 끊긴다. 그래서 프로젝트 전체의 관계(누가 무엇을 호출하고 어떤 테이블을 읽고 쓰는가)와 ERD, 클래스 다이어그램을 소스만으로 얻기 어렵다.

- [확인 필요] 지금은 이 작업을 어떻게 하고 있는가(수작업, 다른 도구 등). 사용자가 말한 적이 없다.

## 2. 목표
- 프로젝트 소스를 주면 Java, MyBatis 매퍼, SQL, 프로시저, JavaScript를 파싱(AST)해 IDE 수준의 콜트리와 관계를 분석한다.
- 분석 결과만으로 ERD를 그릴 수 있다.
- 분석 결과만으로 클래스 다이어그램을 그릴 수 있다.

## 3. 비목표
- 프로그램을 실행하거나 DB에 접속해서 얻는 정보(런타임·동적 분석)는 쓰지 않는다. 테이블 정의는 DDL 파일로 받는다.
- 분석 대상 코드를 고치거나 리팩터링하지 않는다. (제안)
- 코드 품질 검사, 취약점 탐지는 하지 않는다. (제안)
- 정적 분석으로 알 수 없는 관계를 추측으로 채우지 않는다. 알 수 없는 지점은 "미해결"로 남긴다. (제안)
- Oracle, DB2 외의 DBMS와 Spring, MyBatis 외의 프레임워크(JPA 등)는 다루지 않는다. (제안)

## 4. 사용자와 시나리오
주 사용자: [확인 필요] 본인 한 명인지, 다른 개발자에게도 배포하는지.

1. 프로젝트 폴더와 DDL 파일을 주고 분석을 실행해 ERD를 얻는다.
2. 패키지나 클래스를 골라 클래스 다이어그램을 얻는다.
3. 메서드 하나를 골라 호출하는 쪽과 호출되는 쪽의 콜트리를 본다. Java를 넘어 매퍼 SQL과 테이블·프로시저까지 이어진다.
4. (제안) 테이블이나 컬럼을 골라 그것을 읽고 쓰는 SQL, 메서드, 화면을 거꾸로 찾는다.

## 5. 성공 지표
- Java 콜트리가 같은 프로젝트를 IDE의 Call Hierarchy로 본 결과와 일치한다. [확인 필요] 허용 오차.
- DDL에 있는 테이블과 SQL에서 참조한 테이블이 ERD에 빠짐없이 나온다.
- 분석하지 못한 파일과 해석하지 못한 참조가 전부 리포트에 나온다. 조용히 누락되는 것이 없다.
- 검증에는 정답 관계 목록을 함께 둔 직접 만든 샘플 프로젝트(`samples/`)를 쓴다. 공개 오픈소스로 하는 검증은 아직 하지 않았다. (2026-10-11 변경: 공개 프로젝트 8개로 검증을 시작했다. `docs/architecture.md` 11절 참조)
  - 검증 방법: 루트에서 `mvn -q -pl codeatlas-cli verify`를 돌리면 `samples/sample-shop`을 분석해 정답(`expected/`)과 대조하고, 있어야 할 관계의 통과율 100%와 있으면 안 되는 관계(함정) 위반 0을 단언한다. `-Dsample.verify=report`를 붙이면 단언 없이 `codeatlas-cli/target/sample-shop-report.md`에 종류별 통과율과 실패 목록을 쓴다.

## 6. 제약
- 정적 분석만 쓴다.
- 분석 대상: Spring 기반 웹 프로그램과 Spring Batch 기반 배치 프로그램, MyBatis.
- DB: Oracle, DB2. SQL과 프로시저 모두 대상이다.
- 화면: JSP와 JavaScript(React 등) 양쪽을 다루는 범용 도구여야 한다.
- DDL은 파일로 받는다.
- 테스트용 실제 프로젝트가 없다.
- 필요한 파서는 직접 구현할 수 있다.
- 개발은 TDD로 진행한다. (사용자 지시, 2026-10-11)

## 7. 가정과 미확정 사항
사용자가 2026-10-11에 "끝까지 진행"을 위임했으므로 아래 가정을 기본값으로 두고 진행했다. 전부 사용자 검토가 필요하다.

- 가정: "범용"은 화면 기술(JSP, React 등)에 상관없이 쓸 수 있다는 뜻으로 읽었다. 서버 쪽은 Spring, MyBatis로 한정했다.
- 가정: 폐쇄망에 반입할 수 있도록 실행 파일 하나(jar)로 배포하고, 실행 중에 네트워크를 쓰지 않는다.
- 가정: 명령줄로 실행하고 결과는 출력 폴더의 파일(그래프 JSON, 다이어그램, 리포트, 단일 HTML 뷰어)로 받는다. 서버는 띄우지 않는다.
- 가정: 대상 소스는 Java 21 문법까지. 의존 jar는 옵션으로 받거나 프로젝트 안에서 찾고, 없으면 해석 못한 호출을 미해결로 남긴다.
- 가정: 소스 인코딩은 UTF-8을 먼저 시도하고 실패하면 MS949로 읽는다.
- 가정: DB2는 LUW 문법을 기준으로 한다.
- 가정: TypeScript도 대상에 넣는다.
- 가정: iBatis 2.x(sqlMap)는 범위에서 뺀다.
- [확인 필요] 대상 프로젝트의 규모(파일 수). 성능 목표를 정하지 못했다.

구현하면서 정한 범위(각 기능 spec의 가정 절에서 사용자가 알아야 할 것만 옮겼다. 역시 사용자 검토가 필요하다)

- 가정: 애너테이션 처리기는 실행하지 않는다. Lombok은 애너테이션을 보고 생길 멤버(getter, setter, 생성자, 빌더, 로그 필드)를 합성해 콜트리와 생성자 주입이 끊기지 않게 한다. Lombok이 아닌 코드 생성기가 만드는 코드는 다루지 않는다. (F-002, F-003, F-004)
- 가정: JDK 타입(`String`, `List` 등)으로 가는 연관·의존과 JDK 메서드 호출은 기본으로 결과에 넣지 않는다(기록하지 않은 호출 건수만 진단에 남긴다). 그 밖의 라이브러리 호출은 넣는다. `--opt java.includeJdkTypes=true`, `--opt java.externalCalls=all`로 바꿀 수 있다. (F-002, F-003)
- 가정: JSP 스크립틀릿(`<% %>`) 안의 Java 코드는 분석하지 않고 개수만 남긴다. JSP에서는 include, 폼·링크 요청, 인라인 스크립트를 본다. (F-011)
- 가정: Tiles(`<tiles:insertAttribute>`), Struts 태그(`<html:form>`), `web.xml`의 `include-prelude`·`welcome-file`은 다루지 않는다. (F-011) (2026-10-11 변경: Tiles와 SiteMesh는 설정 파일의 정의를 읽어 레이아웃 관계를 기록한다. JSP 안의 `<tiles:insertAttribute>`는 여전히 읽지 않는다. Struts 등 접두사 있는 태그의 URL 속성은 추론 요청으로만 잡는다. 아래 "재검증 뒤에 정한 것")
- 가정: 화면 스크립트에서 HTTP 요청으로 보는 것은 `fetch`, axios, jQuery ajax, `XMLHttpRequest`, 폼 전송, 페이지 이동 등 정해 둔 API다. Vue 단일 파일 컴포넌트(`.vue`), 클라이언트 라우터 이동, GraphQL·WebSocket 클라이언트는 다루지 않는다. (F-010) (2026-10-11 변경: 클라이언트 라우터 이동은 서버 요청과 구분해 기록한다. 아래 "재검증 뒤에 정한 것")
- 가정: 실행에는 JDK 21 이상이 필요하다. JS·TS 분석은 네이티브 라이브러리를 쓰므로 Linux(glibc) x86_64·aarch64, macOS x86_64·aarch64, Windows x86_64에서만 된다. 그 밖의 환경에서는 JS·TS 분석만 건너뛰고 진단을 남기며 나머지 분석은 그대로 한다. 테스트로 확인한 곳은 개발 환경(macOS arm64)이다. (F-001, F-010)
- 가정: `javax.servlet`, `javax.persistence`, `jakarta.*` 같은 Java EE·Jakarta 타입은 JDK가 아니라 라이브러리로 본다(호출과 의존을 기본으로 결과에 넣는다). JDK인지는 분석기를 실행하는 JDK를 기준으로 판정하므로, 대상이 Java 8이어도 `javax.xml.bind`와 `javax.annotation.Resource`는 라이브러리다. (F-002, F-003)
- 가정: Lombok이 만든 멤버로 가는 호출은 컴파일러가 아니라 이름과 인자 수로 찾는다. 같은 이름·인자 수의 후보가 여럿이면 확정이 아니라 추론(`INFERRED`)으로 표시한다. (F-003)
- 가정: jar가 없는 라이브러리 타입의 반환값에 이어 부른 호출 체인(빌더 체인 등)은 링크마다가 아니라 체인당 미해결 1건으로 줄여 남긴다. jar를 주면 해석된다. (F-003)
- 가정: 프로시저·함수·트리거 본문의 동적 SQL(`EXECUTE IMMEDIATE` 등)은 문자열이 리터럴로 완전히 풀릴 때만 분석한다. 풀리지 않으면 리터럴 조각에 테이블 이름이 보여도 테이블을 추론하지 않고 미해결로 남긴다. (F-008)
- 가정: 프로시저 본문의 식 안에서 부른 함수는 DDL에 정의가 있을 때만 호출로 기록한다. 정의가 없는 함수는 내장 함수나 컬렉션 접근과 구분할 수 없어 호출로 만들지 않는다. 문장 자리의 프로시저 호출은 정의가 없어도 기록한다. (F-008)
- 가정: 패키지 안의 오버로드된 프로시저·함수는 구분하지 않고 하나로 본다. Oracle 복합 트리거, 객체 타입 메서드(`TYPE BODY`), Java 저장 프로시저의 본문은 분석하지 않는다. (F-007, F-008)

독립 감사 뒤에 정한 것(2026-10-11. 역시 사용자 검토가 필요하다)

- 가정: CRUD의 R은 그 테이블을 조회하는 구문에만 붙인다. `UPDATE`·`DELETE`·`MERGE`가 바꾸는 테이블의 조건절에서 컬럼을 읽는 것은 R로 세지 않는다(`DELETE … WHERE`는 `D`). (F-015)
- 가정: CRUD 매트릭스에서 주체가 직접 하는 접근은 대문자, 프로시저·함수·트리거를 거쳐서만 닿는 접근은 소문자로 적어 구분한다. (F-015)
- 가정: 공통코드 테이블처럼 복합 키의 일부를 상수 조건으로 채운 조인(`GROUP_CD = 'ORDER_STATUS' AND CODE = …`)은 그 테이블을 부모로 하는 N:1 관계로 확정한다(추론 관계로 표시하고 상수 값을 근거로 남긴다). (F-006, F-018)
- 가정: 같은 부모의 같은 컬럼을 참조하는 두 테이블끼리의 조인(형제 조인)은 테이블 관계로 보지 않는다. ERD에 선을 긋지 않는다. (F-018)
- 가정: React에서 props로 받은 콜백의 호출은 한 가지 형태(함수 컴포넌트가 직접 호출하고, 부모가 JSX 속성으로 프로젝트 함수를 넘긴 경우)만 추론으로 잇는다. 그 밖의 콜백 호출은 잇지 않고 건수만 진단에 남긴다. (F-010)

공개 프로젝트 검증 뒤에 정한 것(2026-10-11, 2차 수정. 역시 사용자 검토가 필요하다)

- 가정: 매퍼 XML이나 DDL이 DB 방언별 파일로 여러 벌 있으면 전부 합치지 않고 한 벌만 골라 쓴다. 기본 우선순위는 `--dialect`로 준 방언, 그다음 Oracle → DB2 → Oracle 계열(Tibero, Altibase) → 그 밖의 방언이다. 무엇을 골랐는지 진단으로 알리고 옵션(`--opt mybatis.dialectVariant=…`, `--ddl`·`--exclude`)으로 바꿀 수 있다. (F-007, F-009) (2026-10-11 변경: 우선순위에 프로젝트 설정이 들어갔다. 아래 "재검증 뒤에 정한 것"의 첫 항목이 이 가정을 대체한다)
- 가정: SQL 스크립트의 데이터 적재 INSERT(한 파일에서 같은 테이블에 리터럴 값을 넣는 구문 10건 이상. 2026-10-11 변경: 판정을 파일 단위로 바꿨다. 10건 이상인 묶음이 하나라도 있거나 INSERT뿐인 스크립트면 그 파일의 리터럴 INSERT를 건수와 상관없이 묶는다)는 구문마다가 아니라 파일·테이블 단위로 묶어 기록하고, CRUD 매트릭스와 콜트리에서는 기본으로 뺀다. 리포트에 파일·테이블·행 수로 요약한다. (F-006, F-015)
- 가정: 벤더(서드파티) 스크립트와 벤더 폴더의 페이지는 기본으로 내용을 분석하지 않고 건너뛴다(건수는 진단에 남긴다). 판정은 경로, 알려진 라이브러리 이름, 라이선스 배너로 하고 옵션으로 끄거나 고칠 수 있다. (F-010, F-011) (2026-10-11 변경: 라이선스 주석만으로 걸린 파일은 그 폴더에서 혼자만 걸렸거나 프로젝트 스크립트가 그 파일의 함수를 많이 부르면 프로젝트 파일로 본다)
- 가정: 화면 스크립트에서 다른 스크립트 파일의 전역 함수를 부르는 호출은 두 스크립트를 함께 싣는 페이지가 확인될 때만 잇는다. 이름만 같다고 잇지 않는다. 그래서 레이아웃 프레임워크(SiteMesh, Tiles)가 붙이는 공통 스크립트로 가는 호출은 이어지지 않는다. (F-010) (2026-10-11 해소: 레이아웃 관계를 읽어 잇는다. "이름만 같다고 잇지 않는다"에도 예외가 생겼다. 아래 "재검증 뒤에 정한 것")
- 가정: 리플렉션 호출은 한 가지 꼴(`x.getClass().getDeclaredMethod("이름", ..)`의 결과를 같은 메서드에서 `invoke(x, ..)`)만 추론으로 잇는다. 그 밖의 `Method.invoke`는 잇지 않고 건수만 진단에 남긴다. (F-003)
- 가정: 대상 외 방언(MySQL 등)의 SQL과 DDL은 "죽지 않고 틀린 사실을 만들지 않는" 수준까지만 읽는다. 그 방언 고유의 구문을 정확히 분석하는 것은 목표가 아니다(3절의 비목표는 그대로다). (F-006, F-007)
- 가정: 테스트 소스(`src/test`)는 기본으로 분석에 넣고 `--exclude-tests`로 뺀다. (F-001)

재검증 뒤에 정한 것(2026-10-11, 3·4차 수정. 역시 사용자 검토가 필요하다)

- 가정: 방언별로 여러 벌인 매퍼·DDL·데이터 적재 스크립트에서 한 벌을 고르는 순서는 직접 준 값(`--dialect oracle|db2`, `--opt mybatis.dialectVariant=<방언>`) → 프로젝트 설정(`Globals.DbType`, JDBC URL 등)이 가리키는 대상 방언 → Oracle → DB2 → Oracle 계열(Tibero, Altibase) → 설정이 가리키는 대상 외 방언 → 그 밖이다. 프로젝트 설정이 MySQL 같은 대상 외 방언이어도 Oracle·DB2 파일이 있으면 그쪽을 쓰고 그 사실을 알린다. `--dialect`는 oracle·db2·auto만 받고, 대상 외 방언으로 분석하려면 `--opt mybatis.dialectVariant=<방언>`을 준다. 결정 기록은 ADR-0010(제안 상태)이다. (F-006, F-007, F-009)
- 가정: 레이아웃 프레임워크는 설정 파일로 읽을 수 있는 것만 다룬다. SiteMesh는 페이지의 `<meta name="decorator">`와 `decorators.xml`·`sitemesh3.xml`, Tiles는 정의 파일이다. Java 설정으로 만든 구성과 JSP 안의 `<tiles:insertAttribute>`는 읽지 않는다. 이 관계는 추론으로 표시한다. (F-011, F-012)
- 가정: 다른 스크립트의 전역 함수 호출은 함께 싣는 근거(같은 페이지, include, 레이아웃)가 없어도 그 이름의 정의가 프로젝트에 하나뿐이면 추론으로 잇는다. 정의가 여럿이면 잇지 않고 건수만 남긴다. (F-010)
- 가정: 클라이언트 라우터(React Router 등)의 화면 전환은 서버 요청과 구분해 기록하고 엔드포인트와 맞추지 않는다. 라우터 패키지를 import한 파일의 이동과 `<Route path>`로 선언한 경로만 알아본다. (F-010, F-012)
- 가정: 요청과 엔드포인트를 맞출 때 같은 모듈에 선언이 있으면 그것으로만 잇는다. 요청 모듈과 대상 모듈이 둘 다 독립 배포 단위(웹앱)면 같은 경로여도 다른 URL로 보고 잇지 않는다(미해결로 남긴다). 게이트웨이나 프록시로 한 주소 아래 묶인 여러 war 사이의 링크는 그래서 이어지지 않는다. (F-012)
- 가정: `action`이 없는 폼은 그 페이지를 직접 그리는 핸들러의 주소로 제출한다고 보고 같은 경로의 엔드포인트와 추론으로 잇는다. (F-011, F-012)
- 가정: 한 호출 지점의 URL 후보가 여럿이면 메서드와 곱하지 않고 URL마다 요청 하나로 기록한다. 메서드와 URL의 짝을 모르면 메서드 후보를 남긴다. (F-010, F-012)
- 가정: 구문 ID가 "리터럴 접두 + 동적"인 `SqlSession` 호출은 그 접두로 시작하고 연산 종류가 맞는 구문이 5개 이하일 때 그 구문들과 추론으로 잇는다. 구문 ID처럼 보이는 문자열을 라이브러리 메서드에 인자로 넘긴 호출은 그 ID의 구문이 실제로 있을 때 추론으로 잇는다. (F-004, F-012)
- 가정: SQL이 참조하는데 DDL에 없는 컬럼은 소속 테이블이 하나로 정해질 때만 그 테이블의 컬럼(DDL에 없음 표시)으로 기록하고, 정해지지 않으면 관계를 만들지 않고 진단만 남긴다. DB가 제공하는 사전 뷰·카탈로그 테이블은 "DDL에 없는 테이블"의 의심 대상에서 뺀다. (F-006, F-008)
- 가정: 조인만으로는 부모·자식을 정하지 못한 추론 관계는 같은 테이블 쌍에 DDL 외래 키가 한 방향으로만 있으면 그 방향을 따른다(카디널리티는 모름으로 둔다). 조인으로 정한 방향이 DDL과 반대이거나 자식 쪽 컬럼이 여러 테이블의 식별자로 쓰이면 방향을 확정하지 않는다. (F-018, F-013)
- 가정: upgrade·patch·migration 스크립트의 외래 키 추가는 대상 테이블·컬럼이 현재 정의에 있으면 관계로 넣는다. 현재 정의가 외래 키를 적는 스키마인데 그 외래 키만 없으면 확정이 아니라 추론으로 표시한다. (F-007)
- 가정: 후보가 여럿이라는 표시(`ambiguous`)는 한 지점에서 둘 이상으로 이었을 때만 붙인다. (F-003, F-012)
